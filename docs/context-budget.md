# コンテキスト使用率の上限

一般設定 → **ツール設定**では、「コンテキスト使用率の上限」だけを変更する。
初期値は**80%**。会話履歴と取得した資料を合わせてモデルの容量の80%まで使用し、
残りを回答のために残す。1回の取得量や通知用の余白はアプリが自動で調整する。
Ollama設定には、このアプリ独自の制御項目を配置しない。

## 設定と互換性

設定APIの形式は次のとおり。値は0より大きく1未満の有限数とし、画面では百分率のスライダーで表示する。

```json
{
  "tools": {
    "context_usage_limit": 0.8
  }
}
```

`GET /api/settings`と`PUT /api/settings`で読み書きする。ツール設定を保存しても、
Ollamaの生成オプションや表示言語を変更しない。各設定画面はその画面の項目だけを更新する。

旧設定の`tool_budget`は読み込み時に移行する。以前の回答予約を残した使用率へ変換し、
既定の回答予約20%は使用率上限80%になる。以前の累積割合・1回割合・安全余白は使用しない。
新しい`tools`があれば優先し、通常の保存時に旧形式を取り除く。
Ollama設定やカスタムプロンプトを移行によって初期化しない。

## 容量の決定と自動調整

- `/api/show`のアーキテクチャ別コンテキスト長をモデル容量として使う。
- ローカルではモデル容量と要求`num_ctx`の小さい方を使い、最初の応答後に`/api/ps`で縮小方向に補正する。
- Cloudではモデル容量を使う。情報取得失敗時は要求値、それも不明なら8192トークンを推定値として使う。
- 古いSDKでもCloud別名を判定できるよう、リモート情報を含む生のモデル情報を保持する。

使用率の上限は会話全体に適用する。ツール結果だけを対象とした独立の累積上限は設けない。
例えば使用率上限80%なら、履歴で既に60%を使用している場合、残り約20%が資料の追加に使える容量になる。
正の`num_predict`が残りの容量より大きい場合は、その回答容量も自動で確保する。
`num_ctx`や`num_predict`自体を変更することはない。

1回のページサイズはモデル容量から内部で決め、現在の空き容量に合わせて縮小する。
通知と最終回答指示の容量を先に確保し、次のツール要求で上限を使い切る前に取得を終了する。
利用者がページサイズや複数の予約割合を計算・設定する必要はない。

## 推定とページング

テキストはUTF-8バイト数÷2を初期推定とし、メッセージ形式・ツール定義・引数も計上する。
画像は初期値として1枚4096トークンを予約する。各ラウンドのOllama実測が推定を超えたら補正係数を引き上げる。
最新の実測入力・生成量・その後の追加結果も下限として使い、過去ラウンドの入力数を累積加算しない。
推定は厳密なトークン数やコンテキスト適合を保証しない。

内蔵・MCPツールには共通の予算を適用する。ページングでは本文・警告・継続情報を合わせて収め、
本文だけを削って読み飛ばすことを防ぐ。非ページング結果の切り詰めは明示する。
画像が収まらない場合もユーザー向け成果物を保持し、モデルには省略を通知する。
呼び出し件数・ラウンド数・結果文字数の固定上限は設けない。
添付プレビュー・HTTP取得サイズなど、別目的の制限は独立して維持する。

## 表示と終了

画面には推定使用率、使用中の容量、設定した上限、モデルの容量を表示する。
内部の予約割合や補正計算は設定画面へ露出しない。
上限に近づくと取得量を減らし、取得済み資料から回答を生成する。
最終回答の入力も収まらない場合は、明確な容量不足エラーを返す。
履歴の自動要約や調査の保存・再開は行わない。

`context_budget`イベントと`done.context_budget`には`context_usage_limit`、`input_limit`、
`input_tokens`、`effective_context`などを含める。`tool_limit`は旧クライアント向けに
`input_limit`の別名として返すが、独立したツール累積上限としては使用しない。
`done.num_ctx`は実効容量、`requested_num_ctx`は要求値とし、最終状態をセッションへ保存する。
旧セッションも読み込める。停止理由は容量不足または継続情報の容量不足とし、通信失敗と区別する。

初期実装の実モデル確認は[検証記録](context-budget-validation.md)に記載する。
