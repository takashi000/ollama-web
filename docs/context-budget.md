# 動的なツール結果予算

ツール結果の上限は、モデルの実効コンテキスト長と現在の空き容量から決める。
文字数による固定の1回上限・累積上限や、呼び出し件数・ラウンド数の上限は設けない。
履歴の自動要約や調査の再開は行わないため、有限のコンテキストを使い切ると取得を終了する。

## 設定

一般設定 → Ollama設定で、実効コンテキストに対する次の割合を変更できる。
`GET /api/settings`と`PUT /api/settings`のトップレベルに`tool_budget`を追加した。
旧形式の設定は各割合を補完して読み込み、次回保存時に新形式で保存する。
既存の生成オプションやカスタムプロンプトを初期化する移行は行わない。

```json
{
  "tool_budget": {
    "total_ratio": 0.5,
    "per_result_ratio": 0.05,
    "response_reserve_ratio": 0.2,
    "safety_margin_ratio": 0.1
  }
}
```

各値は有限の正数とし、1回の割合は累積以下、累積＋回答予約＋安全余白は1未満とする。
正の`num_predict`が割合で求めた回答予約を超える場合、その値を予約する。
`num_ctx`や`num_predict`を予算管理によって自動変更することはない。

## 実効コンテキストの決定

| 条件 | 使用する容量 | 取得元 |
|---|---|---|
| ローカルでモデル容量・要求値が判明 | 小さい方 | `model`または`requested` |
| ローカルで片方だけ判明 | 判明している値 | `model`または`requested` |
| Cloudでモデル容量が判明 | モデル容量 | `model` |
| モデル情報が取得できない | 正の要求`num_ctx` | `requested` |
| どちらも不明 | 8192トークンの推定値 | `fallback` |

モデル容量は`/api/show`の`model_info.general.architecture`に対応する
`<architecture>.context_length`を参照する。モデル能力と同じ取得結果をリクエスト内で再利用する。
Cloudはリモート情報またはCloudモデル名で判定する。取得失敗、廃止モデル、欠落情報でも代替値を使う。

ローカルでは最初の応答後に`/api/ps`を確認する。同じモデルの割り当て容量が初期値以下なら、
`runtime`へ補正する。容量を拡大する方向には補正しない。別リクエストによる同一モデルの
再ロードとの完全な対応付けはできないため、取得元を表示する。Cloudにはこの補正を適用しない。

## 推定と実測補正

テキストはUTF-8バイト数÷2の切り上げを初期推定とする。送信するツール定義・引数も含め、
メッセージごと32、リクエストごと256トークンを形式上の余裕として加える。
画像は初期値として1枚4096トークンを予約する。画像のバイナリサイズからトークン数を換算しない。

各ラウンドの`prompt_eval_count`が送信前の推定を超えた場合、補正係数を引き上げる。
最新の実測入力＋生成量＋その後の追加結果も、次の入力推定の下限として使用する。
入力数をラウンド間で累積加算せず、取得済み結果を入力から二重に差し引かない。

```text
次の結果予算 = max(0, min(
  実効容量 × 1回割合,
  実効容量 × 累積割合 − 取得済み結果,
  実効容量 − 次の入力全体 − 回答予約 − 安全余白 − 通知用予約
))
```

残量が1回上限より小さくても、取得量を縮小して実行する。
ページングでは本文・警告・継続トークン・PDF再開情報を合わせて予算内へ整形する。
単独で実行するツールにはLLM向けの予算を適用せず、既存の取得希望量を使用する。
添付プレビューやHTTP取得サイズなど、別目的の制限は独立して維持する。

任意のMCPツールへ予算パラメーターを追加送信することはない。
結果を秘匿化し、必要なメディア通知を加えてから共通予算を適用する。
非ページング結果は切り詰めを明示し、ページング結果は部分的に返さず境界エラーにする。
自動再実行はしない。画像が収まらない場合、ユーザー向け成果物は保持し、モデルには省略を通知する。

推定は厳密なトークン数やコンテキスト適合を保証しない。特に初回・未知のモデル・画像入力では差がある。
画面には推定と実測を区別して表示する。

## 状態と停止理由

`context_budget` SSEイベントと`done.context_budget`に、以下の情報を含める。

- `effective_context`、`requested_num_ctx`、`source`、`capacity_estimated`
- `estimated`（使用量は常に推定）、`input_tokens`、`tool_tokens`、`tool_limit`
- `next_result_tokens`、`response_reserve`、`safety_margin`、`correction_factor`、`ratios`
- `stop_reason`

| 停止理由 | 動作 |
|---|---|
| `tool_total_limit` | 累積予算を使い切り、取得済み情報から回答する |
| `context_headroom` | 会話と予約容量の余裕が不足。最終回答の入力も収まらなければ容量不足エラーを返す |
| `result_metadata_too_large` | ページ継続情報が収まらない。同じバッチの小さな要求を評価してから取得を終了する |

事前にページ情報が収まらないと分かる内蔵ツールは実行せず、実行イベントを送らない。
取得後にURLリダイレクトなどで情報が増えた場合は、実行済みの失敗として扱う。
未実行要求にも対応するtoolメッセージを残すため、バッチの通知容量を先に予約する。
通信失敗は予算停止とは別のエラーとして扱う。

`done.num_ctx`は実効容量、`done.requested_num_ctx`は要求値とする。
最終予算をセッションの`token_count.context_budget`に保存する。旧セッションも読み込める。
ログには容量の根拠・各ラウンドの推定と実測・補正・停止理由を残し、本文や秘密情報は追加記録しない。

## 検証

容量の解決、設定移行、Unicode推定、実測補正、同時実行の分離、残量の活用、
予算変更中のページ連結による原文復元、旧固定上限を超える継続、保存・日英表示をテストする。
実モデルでの確認結果は[検証記録](context-budget-validation.md)に記載する。
