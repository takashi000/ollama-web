# 動的予算の検証記録

以下の実モデル計測は、4つの割合を使っていた初期実装時点の記録である。
現在の設定は[使用率上限1項目](context-budget.md)へ変更しており、これらの割合を設定する画面はない。

実施日：2026-10-26。既存のOllama 0.40.11へ接続し、ユーザーの会話・添付を使わず、
英語・日本語・Python・JSONを組み合わせた固定の合成資料を返す`lookup`ツールで確認した。
要求は`num_ctx=32768`、`num_predict=256`、`temperature=0`。予算割合は既定値を使用した。

| 項目 | ローカル | Cloud |
|---|---|---|
| モデル | `hf.co/unsloth/gemma-4-E2B-it-qat-GGUF:UD-Q4_K_XL` | `muse-spark-open:cloud` |
| 実効コンテキスト | 32768 | 1048576 |
| 最終的な容量の取得元 | `/api/ps`の実行時割り当て | `/api/show`のモデル情報 |
| ツール実行 | 1回 | 1回 |
| 結果の推定トークン数 | 1638（1回予算へ縮小） | 3345（全文） |
| 最終回答リクエストの入力推定 | 2567 | 4090 |
| 最終回答の`prompt_eval_count` | 994 | 2184 |
| 最終回答の`eval_count` | 2 | 162 |
| 補正係数 | 1.0 | 1.0 |
| 処理時間（ロード・通信込み） | 8.53秒 | 2.89秒 |
| エラー・予算による停止 | なし | なし |

両ケースとも入力推定は実測より保守的だった。Cloudでは要求値でモデル容量を縮小せず、
ローカルでは要求値と実行時割り当てを使う動作を確認した。この小規模な確認は、
全モデル・全入力の推定精度や性能を保証するものではない。

`qwen3-coder-next:cloud`と`qwen3.5:cloud`ではモデル情報を取得できなかった。
情報取得失敗時に空のメタデータを返し、要求容量へフォールバックすることは自動テストでも確認した。

自動テストでは、上記の実測確認とは別に次を検証する。

- 大きなコンテキストで旧累積文字数制限を超えて5ラウンド以上継続し、動的予算で停止する。
- 1回上限未満の残量を使い、同一バッチの小さな要求を実行する。
- 日本語・英語・コード・JSON・画像の推定と、過少推定時の補正係数の引き上げ。
- テキスト・PDFを異なる予算でページングし、取得本文から原文を欠落なく復元する。
- ページ情報の事前検査、MCPの結果・画像省略通知、並行実行時の分離。
- 旧設定の補完、最終予算のセッション保存、日英の設定検証と再読み込み後の表示。

全体回帰確認は319件成功、任意の実モデルUIテスト2件はスキップした。
日英の新しいブラウザテストと既存の停止・再送テストを含む。
その後、SDKがCloud別名のリモート情報を落とす場合と実測カウンター欠落時の保存を追加検証し、
モデル情報・予算・設定関連79件が成功した。Ruffとmypyも成功した。

ブラウザ検証には作業フォルダー内へ配置したPlaywright Chromiumを使用した。
外部サービスの停止操作を伴う任意UIテストは実行せず、実モデルの予算確認は上表の合成資料で行った。

## 使用率上限1項目への変更後

一般設定の直下にツール設定を設け、上限80%のスライダー1本へ変更した。
独立した累積割合・1回割合・回答予約割合・安全余白の設定を廃止し、
会話と取得資料の合計へ使用率上限を適用する。

全体回帰テスト325件成功、任意の実モデルUIテスト2件スキップ。
日英ブラウザで配置・単一スライダー・保存・再表示・Ollama設定の保持を確認した。
旧4項目からの移行、履歴も含めた使用率制御、旧累積50%を超える取得、
最終回答用の容量を残して終了するケースも検証した。Ruffとmypyは成功した。
